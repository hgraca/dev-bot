## `Glob` and `find` miss gitignored paths — issue folders under `storage/` are invisible to default search

Iter-9 audit folder lives at `storage/self-improvement/improve-planning/iteration-9/.ai/devbot/memory/work/active/<task-folder>/`. `storage/` is gitignored (line 10 of `~/.gitignore`). Both `Glob` (which honours `.gitignore` in this opencode environment) and `find` from the repo root _with default skip rules or shell pipelines that filter_ return zero matches for paths inside `storage/`, even though the files exist on disk. Symptom: orchestrator concludes "iter-N artefacts not produced" when in fact they exist at the canonical SKILL-prescribed path under `<issue-folder>`. Direct `Read` of the canonical path works because `Read` does not consult `.gitignore`. **Fix when searching for issue-folder artefacts:** (1) prefer `Read` with the known canonical path from the SKILL spec (`<issue-folder>/PLAN-ARCH-YYYY-MM-DD-NNN.md`, `<issue-folder>/backlog.md`, etc.); (2) when discovery is required, use `ls` via `bash` with an explicit absolute path into the gitignored area, OR `find <abs-path> -type f` which walks the filesystem directly without `.gitignore` filtering; (3) for content search inside gitignored areas, use `grep -r` via `bash` with `--no-ignore` semantics (ripgrep: `rg --no-ignore`). The `search-code` SKILL recommends `Glob` for path lookups but does not flag the gitignore-blindness — see `src/skills/dev/search-code/SKILL.md` updated note. Self-improvement folders (`storage/self-improvement/`), local memory (`storage/projects-memory/`), and the opencode binary tree (`storage/opencode-src/`) are all gitignored. When the user asks "did the agent produce X under storage/", do not rely on `Glob` or default `find` — read the expected canonical path directly. Confirmed via iter-9 evaluation session 2026-05-08: `Glob "storage/self-improvement/improve-planning/iteration-9/**/PLAN-ARCH-*.md"` returned "No files found" while the file existed at exactly that path.
