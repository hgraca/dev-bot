# Kubernetes Access

How an agent reaches the GET-E clusters: through the `kctl-<key>` MCP
servers the `k8s` module registers. The kubeconfig is **generated per project**
by the module's `init.sh`; never hand-edit it, never point `kubectl` at
`~/.kube/config`, and never run `kubectl` in a shell at all.

## When to Apply

- Reading cluster state: pods, logs, deployments, events, ArgoCD applications
- Debugging why a workload is crash-looping, unready, evicted or not deployed
- Confirming a deploy landed (image tag, rollout status, pod start time)

## Never run kubectl in a shell

The module's always-on memory forbids it in every channel: the bash tool, PTY
sessions, scripts, Makefiles, `ssh …`, `docker exec … kubectl`,
`KUBECONFIG=… kubectl`, and the `k` alias. `devbot kctl run|exec` is a shell
command that runs kubectl too — it is for the human, not a workaround.

The shipped guard rules enforce the direct forms (`kubectl`, the `VAR=… kubectl`
prefix, `kubectl` inside `bash -c`/`xargs`/`ssh`/`docker exec`, and
`devbot kctl run|exec`). They are a backstop: a hook sees a shell command, not
what a script or a Makefile recipe does, so the memory's rule is the one that
binds.

Use the MCP server named for the cluster instead. Each selected cluster is its
own server with one tool:

```jsonc
// server: kctl-gete-dev   tool: kubectl
{ "args": ["get", "pods", "-n", "core"] }
{ "args": ["logs", "-n", "core", "deploy/transfers", "--tail=100"] }
{ "args": ["get", "applications", "-n", "argocd"] }
{ "args": ["auth", "whoami"] }
```

`args` is kubectl's argv — **one element per argument**, no leading `kubectl`
(refused), no `--context`/`--kubeconfig`/`--server`/`--cluster`/`--user`/
`--token` (refused), and no `kubectl config` write subcommand (refused: the
kubeconfig is generated by `devbot reinit`). The server applies the cluster's
kubeconfig and context for you; that is why the tool has no target argument to
get wrong.

If the server you need is not in the tool list, this project has no cluster
access: report it and ask the human to run `devbot reinit <project>`. Do not
fall back to a shell.

## What the identity can do

`kubectl auth whoami` (through the MCP) shows the groups the credentials land in:

| Group                  | Grants                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `gete-agents-readonly` | cluster-wide `get/list/watch` — including `pods/log` — with **no** secrets, exec, port-forward or token creation |
| `gete-agents-writer`   | staging only: create/update/patch/delete workloads in the **`default`** namespace                                |

Consequences worth remembering:

- `pods/exec` is denied by design. To inspect a datastore, use the `datasources`
  module or the SigNoz metrics rather than trying to exec into the pod.
- The writer Role is namespaced to `default`. `core`, `kube-system`, `argocd` and
  `otel-collector` are read-only even on staging.
- No secrets are readable — never attempt `get secret`, and never ask for one to
  be added to the role.

## Why not plain kubectl

- The generated file is `~/.kube/devbot/<project_name>-<8-hex>.yaml`; the hash
  is derived from the absolute project path and is not guessable.
- The generated contexts (`gete-prod-ro`, `gete-staging-rw`) use the devbot AWS
  profile. The contexts in `~/.kube/config` use **SSO**; when that session lapses
  they fail with `Token has expired and refresh failed`. That error means wrong
  kubeconfig, not no access.
- Each project's file contains only the clusters that project opted into. Two
  projects cannot widen each other's access.
- Credentials come from the catalogue's `credential_env`: each entry exports its
  key (`AWS_ACCESS_KEY_ID`) from the `${VAR}` it references (`AWS_KEY`), read
  from the environment at call time. `kctl.sh` verifies them before exec, so a
  missing variable is reported by name instead of as an opaque plugin error.

## Gotchas

- **After changing `.devbot.project.jsonc` or the global `kubectl` catalogue, run
  `devbot reinit <path>`.** The kubeconfig is rendered, not read live, and the
  MCP servers are published from the rendered set — a stale project lists the
  previous selection.
- **The default context is chosen by project name**, so `k8s-gete-dev` opens on
  `gete-staging-rw` and `k8s-gete` on `gete-prod-ro`. Through the MCP this is
  implicit: the server's cluster decides its context.
- **Production is read-only.** There is no writable production context; manifest
  changes go through the GitOps repo (`k8s-gete`) and ArgoCD.
- **Do not apply manifests on staging** unless the task says so — staging is also
  ArgoCD-managed from `k8s-gete-dev`, and an imperative apply is reverted on the
  next sync.
