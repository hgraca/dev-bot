# Skill: Atomic Design

[Brad Frost's atomic design](https://bradfrost.com/blog/post/atomic-web-design/) structures a UI as
five tiers, each composed of the ones below it. It is framework-agnostic — the tiers are about
_composition and responsibility_, not about any particular library.

## The five tiers

| Tier          | What it is                                          | Examples                          |
| ------------- | --------------------------------------------------- | --------------------------------- |
| **Atoms**     | Single-purpose, no composition; the smallest units  | `Button`, `Input`, `Icon`, `Tag`  |
| **Molecules** | A small group of atoms working as one unit          | `Card`, `Form`, `SearchBar`       |
| **Organisms** | A distinct page section built from molecules        | `Header`, `Footer`, `Hero`        |
| **Templates** | A page-level layout with placeholder content        | `BaseLayout`, `DashboardTemplate` |
| **Pages**     | A template bound to real data, routed to by the app | `UserProfile`, `UserList`         |

## Rules

- **Lowest tier that fits** — place a component at the lowest tier that describes it; only promote
  it when it genuinely composes the tier below.
- **Compose downward only** — a tier imports from the tier below it, never above. An atom never
  imports an organism; a molecule never imports a template.
- **Colocate** — a component's markup, styles, test, and story live together in the component's
  directory, with a barrel `index` re-export.
- **Name by intent** — `UserCard`, not `Card2`. PascalCase for component files; the framework's
  route-file convention (kebab-case) applies only inside the routing directory.
- **Compose primitives, don't re-implement them** — a generated primitive library (shadcn/ui,
  Radix, …) supplies the unstyled building blocks; the tiers wrap and compose those rather than
  reimplementing a button or a dialog.

## Structure (framework-agnostic)

```
components/
├── atoms/          ← single-purpose (Button, Input, Icon)
│   └── Button/
│       ├── Button.<ext>          ← the component
│       ├── Button.test.<ext>     ← unit test
│       ├── Button.stories.<ext>  ← story
│       └── index.<ext>           ← barrel re-export
├── molecules/      ← atom groups (Card, Form)
├── organisms/      ← page sections (Header, Footer)
├── templates/      ← layout compositions (BaseLayout)
└── pages/          ← template + data (UserProfile)  [see mapping]
```

## Reference setup (React + Vite + TypeScript)

The React examples below assume this layout. The tiers are the same in any stack; the paths and
aliases adapt to the bundler.

```
src/
├── components/
│   ├── design-tokens.css        ← :root (light) + .dark tokens, imported by the entry point
│   ├── atoms/<Name>/…
│   ├── molecules/<Name>/…
│   ├── organisms/<Name>/…
│   └── templates/<Name>/…
├── pages/<Name>/…
└── main.tsx
lib/
└── shadcn/                      ← generated primitives (button.tsx, card.tsx, …)
```

- **Aliases** — app code imports through `@/*` → `src/*`; the primitives through `@lib/*` → `lib/*`.
  Declare both in the tsconfig `paths` and the bundler (`resolve.alias`); a mismatch shows up as an
  unresolvable import at build time, not at type-check time.
- **Primitives live outside the tiers** — `lib/shadcn/*` is generated by the shadcn CLI and treated
  as vendored source. The tiers compose it (`atoms/Button` wraps `lib/shadcn/button`) so the library
  has one place to swap or restyle a primitive.
- **Design tokens are CSS custom properties**, not a JS theme object. They are declared in
  `src/components/design-tokens.css` under `:root` (light) and `.dark` (dark) — `--background`,
  `--foreground`, `--primary`, `--muted`, `--border`, `--ring`, `--radius`, … — and Tailwind v4 maps
  them to utilities through the `@theme inline` block in the same file. With Tailwind v4 there is no
  `tailwind.config.js`; that file is the source of truth. Change a token there and every tier follows.
- **Every component folder carries its test and its story** next to the component plus an `index.ts`
  barrel, so a tier folder is self-contained and reviewable on its own.

### Theming

Light and dark are the same tokens under two selectors: `:root` holds the light values and `.dark`
overrides them. The dark values are unreachable until something applies that class, so a toggle is
part of the setup, not an afterthought — the app shell applies it to a root element, and Storybook
applies it to the preview (see the `devbot:storybook` skill). A third theme is another class block
plus its selector, never per-component changes.

## React examples

```tsx
// src/components/atoms/Button/Button.tsx
import type { ComponentProps } from "react";
import { Button as BaseButton } from "@lib/shadcn/button";

export type ButtonProps = ComponentProps<typeof BaseButton>;

export const Button = (props: ButtonProps) => <BaseButton {...props} />;
```

```tsx
// src/components/molecules/Card/Card.tsx
import type { ReactNode } from "react";
import {
  Card as BaseCard,
  CardContent,
  CardHeader,
  CardTitle,
} from "@lib/shadcn/card";

export interface CardProps {
  title?: string;
  children?: ReactNode;
}

export const Card = ({ title, children }: CardProps) => (
  <BaseCard>
    {title && (
      <CardHeader>
        <CardTitle>{title}</CardTitle>
      </CardHeader>
    )}
    <CardContent>{children}</CardContent>
  </BaseCard>
);
```

```tsx
// src/components/organisms/Header/Header.tsx
import type { ReactNode } from "react";

export interface HeaderProps {
  title: string;
  actions?: ReactNode;
}

export const Header = ({ title, actions }: HeaderProps) => (
  <header className="flex items-center justify-between gap-4 border-b px-6 py-4">
    <span className="text-lg font-medium">{title}</span>
    {actions && <div className="flex items-center gap-2">{actions}</div>}
  </header>
);
```

```tsx
// src/components/templates/BaseLayout/BaseLayout.tsx
import type { ReactNode } from "react";
import { Footer } from "@/components/organisms/Footer";
import { Header } from "@/components/organisms/Header";

export interface BaseLayoutProps {
  title: string;
  footer?: ReactNode;
  children: ReactNode;
}

export const BaseLayout = ({ title, footer, children }: BaseLayoutProps) => (
  <div className="flex min-h-screen flex-col">
    <Header title={title} />
    <main className="flex-1 px-6 py-8">{children}</main>
    <Footer>{footer}</Footer>
  </div>
);
```

## Svelte examples

```svelte
<!-- src/lib/components/atoms/Button/Button.svelte -->
<script lang="ts">
  import type { Snippet } from "svelte";

  let { variant = "primary", children, ...rest }: { variant?: "primary" | "secondary"; children: Snippet } = $props();
</script>

<button class="px-3 py-2 rounded-lg {variant === 'primary' ? 'bg-primary text-primary-foreground' : 'bg-secondary text-secondary-foreground'}" {...rest}>{@render children()}</button>
```

```svelte
<!-- src/lib/components/organisms/Header/Header.svelte -->
<script lang="ts">
  import Navbar from "$lib/components/molecules/Navbar/Navbar.svelte";
</script>

<header class="border-b px-6 py-4">
  <Navbar />
</header>
```

```svelte
<!-- src/lib/components/templates/BaseLayout/BaseLayout.svelte -->
<script lang="ts">
  import type { Snippet } from "svelte";
  import Header from "$lib/components/organisms/Header/Header.svelte";
  import Footer from "$lib/components/organisms/Footer/Footer.svelte";

  let { children }: { children: Snippet } = $props();
</script>

<div class="flex min-h-screen flex-col">
  <Header />
  <main class="flex-1 px-6 py-8">{@render children()}</main>
  <Footer />
</div>
```

## Gotchas

- **Don't force it** — if a component doesn't clearly sit in a tier, keep it nearest its use until it
  does; the tiers are a guide, not a quota.
- **Templates vs pages** — a template has no real data; the page is where a template meets a
  route/loader and real content.
- **Framework routing wins** — Next.js `app/` and SvelteKit `src/routes/` own routing; atomic design
  structures the _components_ those routes render, not the routes themselves.
- **Where the tiers live differs per framework** — Next.js and Vite put them under
  `src/components/<tier>/<Name>/`, SvelteKit under `src/lib/components/<tier>/<Name>/`. The pages
  tier is often the framework's routing directory rather than a sibling `pages/` folder.
- **Never put tokens in a `tailwind.config.js`** on Tailwind v4 — the config is CSS-first; tokens are
  custom properties in the stylesheet, and a JS config silently diverges from them.
- **A tier importing upward compiles fine and is still wrong** — the compiler will not catch a
  molecule importing a template; that is a review catch.
