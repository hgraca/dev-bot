## `datasources` gains a sidecar class for sources toolbox cannot host

A datasource whose `type` is not an mcp-toolbox engine is served by its own MCP server, not by the shared gateway. `render_tools_yaml.py` holds a `SIDECARS` registry, skips those entries (no toolbox source, tool or toolset) and hands them to `render_compose.py`, which renders one streamable-http service per sidecar; `init.sh` points each `datasources-<name>` manifest at that service's own `/mcp`. The declaration shape is unchanged — a `type` and an `env` map — so no new config key reaches the user, and `validated_items` still applies the name/unknown-key/`env`-shape checks plus a sidecar-specific check that every `env` key is one the server consumes. Ports are `DATASOURCES_PORT + 10 + index` over the **sorted** names (so a reinit renders byte-identical ports) and are published to `init.sh` by `render_compose.py --sidecar-ports`, which keeps the manifest URL and the service listener from drifting. Credentials follow the module's rule: env **names** only, with values interpolated by compose from the environment `devbot up` builds, and nothing mounts `~/.aws` — an AWS-facing sidecar takes `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_SESSION_TOKEN`.

Three decisions are counter-intuitive and will be re-flagged otherwise. (1) Sidecars are **not** probed by the availability oracle: each is its own container, so it cannot take the shared gateway down, and the canary exists precisely because toolbox treats one unreachable source as fatal. (2) Each service is brought up **independently** — `up -d --no-deps datasources-mcp` for the gateway, `up -d --build <svc>` per sidecar — because `docker compose up` fails as a unit when any service's image or build context cannot be prepared, which would otherwise re-couple a sidecar's failure to the gateway. (3) Sidecars bypass `available_catalogue.py`'s env-completeness filter entirely, so the render emits a `WARN` for an unset `${VAR}` instead of excluding the source. Shipped sidecars: `opensearch` (the OpenSearch project's `opensearch-mcp-server-py`, version pinned in `versions.env`) and `s3` (dev-bot's own read-only server under `src/agentic/datasources/s3-mcp/`, dependencies baked into its image, four tools with no mutating call, and `get_object` refusing rather than truncating above `S3_MCP_MAX_GET_BYTES`).
