## Canonical MCP manifests may declare `headers`, with `{env:VAR}` allowed to be embedded

The canonical module manifest (`src/agentic/<module>/mcp.json`) gains `headers` as a first-class key (`ENTRY_KEYS` in `src/_shared/mcp_translate.py`) — http-only, a string→string map, rejected on stdio exactly as `oauth` is. Critically, it relaxes the `{env:VAR}` rule for headers only: an env VALUE must still be the whole value, but a header VALUE may embed the token (`"Sentry-Bearer {env:SENTRY_ACCESS_TOKEN}"`), because an upstream API carries its scheme prefix on the same value and cannot be split. Before this, an authenticated remote MCP was inexpressible — no token could reach a remote server — which is what blocked the sentry module. Both harnesses expand an embedded token: opencode's config interpolation is a global regex replace (`text.replace(/\{env:([^}]+)\}/g, …)`, verified against the installed binary) and Claude Code expands `${VAR}` in `headers` (verified against Anthropic's docs), so the translator emits `{env:VAR}` verbatim for opencode and rewrites an embedded `{env:VAR}` to `${VAR}` for claudecode, never resolving a secret into a config file. Two guards keep the relaxation honest: validation rejects a malformed `{env:…}` fragment and rejects a canonical `${VAR}` (which would stay literal on opencode while claudecode expanded it), and the check keys off field presence so `"headers": null` is rejected rather than written through. The contract's two other consumers moved with it — `mcp_env_refs.py` scans canonical headers with `finditer` so a missing token is flagged at init, and `mcp_key_is_current.py` drops any header carrying an env-ref token from both sides of its comparison so a resolved-vs-token header never reads as stale. A token-authenticated remote manifest declares `oauth: false` alongside it, so opencode's automatic OAuth discovery cannot race the token.
