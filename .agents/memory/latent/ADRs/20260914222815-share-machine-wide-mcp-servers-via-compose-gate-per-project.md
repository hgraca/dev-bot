## Gate heavy MCP servers per project; share stateless ones machine-wide via docker compose

devbot boots one harness instance per project, and each instance spawns its **own full set of MCP servers**. Measured on one machine with four concurrent instances (2026-09-14): ~5.8 GB RSS total across the four harness trees, ~1.78 GB of it in the MCP server copies alone. The same stateless servers (`mdctx`, `signoz`, `codebase-memory`, `svelte`) were rebuilt four times; only per-project/per-instance servers genuinely differ per instance. Tool-schema cost measured via real `tools/list` handshakes: chrome-devtools ~6.5k tokens, codebase-memory ~5.9k, playwright ~3.5k — a session running all local module servers starts with ~17.5k tokens of MCP schemas before any conversation.

**Decision — a dual-layer model.**

**Layer 1: per-project gating (the default, config-only).** A project pays only for the servers it uses. Module enablement stays the canonical gate (ADR `20260908213000` module-gate policy unchanged); a project opts out of _heavy per-instance servers_ (chrome-devtools, playwright, graphify, signoz…) by **disabling the server's module** (`disabled_modules`) — decided 2026-09-14: module-level only, no new per-server config key. opencode's runtime `mcp.<name>.enabled: false` is honored (verified: config is load-once, not hot-reloaded) and remains the local escape hatch for disabling an inherited server without unregistering it. Measured schema costs and the lever are documented in `docs/mcp-config.md`.

**Layer 2: shared machine-wide MCP layer via docker compose.** **Principle (user, 2026-09-14): dev-bot never configures an MCP server that launches its own per-instance process.** If a server is needed it is configured as **remote** (http), hosted in a docker container shared across instances. Servers proven stateless and machine-global run **once** per machine as compose services; harnesses connect over http (MCP streamable-http / SSE) instead of N stdio copies. This follows the existing `src/tools/{ollama,litellm}/docker-compose.yml` pattern auto-discovered by `devbot up`/`down`. Initial candidates by T0.3 classification, in rollout order (mdctx moved first — it is enabled in this instance, so the mechanism could be verified live):

| server            | why shareable                                                                                                |
| ----------------- | ------------------------------------------------------------------------------------------------------------ |
| `signoz`          | fixed org endpoint + env token; stateless client; heaviest stdio cost (83–94 MB/instance)                    |
| `svelte`          | `@sveltejs/mcp` docs server, no project binding                                                              |
| `mdctx`           | index root is dev-bot's machine-global `storage/global-memories`                                             |
| `codebase-memory` | tools take `repo_path` per call (`index_repository`/`list_projects`); already forks a shared internal daemon |

Explicitly **not** shared (stay per-instance stdio): `chrome-devtools`, `playwright` (browser context per session), `devbot-tools`, `graphify`, `codebase-index` (`--project .`), `react/next-devtools` (project dev-server binding). `context7` and `websearch` are already remote.

**Accepted trade-offs.** Requirement: each shared server must support an http transport (or run stdio behind a tiny gateway); a server that can't stays per-instance rather than forcing the design. A single daemon port per machine needs collision-safe defaults (lesson: codebase-memory's fixed port 9749 collided across instances) — dev-bot gateways use the `18500–18599` block on `127.0.0.1`. Token schemas of shared servers are still injected per session — layer 2 saves RAM/CPU, not tokens; the token cost is owned by layer 1 (gating) and T2.2.

**Implementation (mdctx, 2026-09-14 — first conversion).** `src/agentic/mdctx/` gained a `Dockerfile` (node:22-slim + `mcp-proxy==0.12.0` + `mcp<2` + `mdctx@0.1.0`) and a `docker-compose.yml` (service `mdctx-mcp`, `127.0.0.1:18501:18501`, global-memories + `.mdctx` mounted, image built on first `devbot up`). `mcp.json` flipped to `{"type":"http","url":"http://127.0.0.1:18501/mcp"}`; a module `up.sh` waits for the gateway before the harness starts. Verified live: the container serves a valid MCP `initialize` over streamable-http at `/mcp`, and `devbot reinit` refreshed the opencode entry from `local` to `remote`. The host mdctx **CLI** stays installed — the memory module's tools (search-memories, reindex) use it directly; only the MCP server moved into the container.

**Implementation (signoz, 2026-09-15 — second conversion).** `src/agentic/signoz/` gained a `docker-compose.yml` using the **official image** `signoz/signoz-mcp-server:v0.14.0` with `TRANSPORT_MODE=http` (native HTTP at `/mcp` — **no bridge needed**), `127.0.0.1:18502:8000`, `SIGNOZ_API_KEY` from `${SIGNOZ_AUTH_TOKEN}` in the environment. `mcp.json` flipped to `{"type":"http","url":"http://127.0.0.1:18502/mcp"}`; a module `up.sh` waits for the gateway and warns when the token is unset. The per-machine binary download (34 MB) and the per-harness binary symlink were **removed** — `install.sh` now only installs skills, `init.sh` only symlinks them. `signoz` was added to opencode's `REFRESH_MODULES` so existing configs pick up the new shape (registration is skip-if-exists). Verified live: container serves a valid MCP `initialize` at `/mcp`; `devbot reinit` refreshed the opencode entry `local` → `remote`.

**Implementation (svelte, 2026-09-15 — third conversion).** `src/agentic/svelte/` gained a `Dockerfile` (node:22-slim + `mcp-proxy==0.12.0` + `mcp<2` + `@sveltejs/mcp@0.1.26`) and a `docker-compose.yml` (service `svelte-mcp`, `127.0.0.1:18503:18503`, image built on first `devbot up`). `mcp.json` flipped to `{"type":"http","url":"http://127.0.0.1:18503/mcp"}`; a module `up.sh` waits for the gateway. `svelte` joined opencode's `REFRESH_MODULES`. **Project-independence verified empirically**: the server is stateless w.r.t. the project (documentation is bundled; `svelte-autofixer` receives the code in the tool call), so a single shared container serves every project — confirmed by calling `svelte-autofixer` against a snippet with no project mounted, which correctly reported the Svelte 5 issues (`on:click` deprecated, non-reactive `count`).

**Follow-up work.** (1) Standardize versions pinning across enabled binaries (done for chrome-devtools/playwright in T1.2; extend to svelte/next-devtools when enabled). (2) Layer 1 is documentation-only — module-level disablement is the gate (no new config key). (3) T3.3 — mdctx done; remaining: `signoz` (official image + native `TRANSPORT_MODE=http`, no bridge needed), `svelte`, `codebase-memory` (both stdio → bridge). Verify transport support per server before moving it. (4) T4.1 — a `devbot` runtime-footprint report to keep these numbers measurable.
