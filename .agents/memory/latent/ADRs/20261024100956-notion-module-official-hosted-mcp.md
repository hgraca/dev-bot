## `notion` module wires Notion's official hosted MCP server

dev-bot gained a module (`src/agentic/notion/`) giving agents read and write access to Notion through Notion's **official hosted** MCP server (`https://mcp.notion.com/mcp`, Streamable HTTP, OAuth auto-detected by opencode because the canonical manifest omits `oauth`) rather than the open-source `notion-mcp-server`, which Notion no longer actively maintains and which needs a hand-provisioned integration token. It is a pure-declaration module (one canonical `mcp.json` + `skills/SKILL.md` + `docs.md` + bats), no lifecycle scripts and no host binary. Three decisions to preserve. (1) Both gates are off by default: `"notion": false` in the dist `modules` map _and_ `"enabled": false` in `mcp.json`. The dist `modules` map is never merged into an existing runtime config, so on an upgraded install the absent key reads as enabled — on opencode the server is then registered but still not started, because the MCP gate does not depend on the map. (2) The skill teaches workspace discovery (`notion-get-self`, `notion-get-tool-access`) before any call, because a workspace-owned connection exposes only the tool subset an admin selected and the hosted server's hyphenated `notion-*` names differ from other implementations. (3) Writes are propose-confirm-act, and the skill requires reading the returned `warnings` array, since a write can succeed after repairing or dropping part of the input. Caveat: enablement differs per harness — opencode emits the entry with `enabled: false` and the user flips that value in `opencode.jsonc`, while Claude Code has no per-server on/off and `_wire_mcp` omits a disabled server from `.mcp.json` entirely, so enabling it there means setting `enabled: true` in the canonical manifest and reiniting.
