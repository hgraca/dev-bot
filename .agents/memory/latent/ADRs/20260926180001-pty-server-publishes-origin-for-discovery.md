## The PTY server publishes its origin to a runtime file instead of the sidebar scanning `/proc`

The panel used to find the server by scanning `/proc/self/net/tcp{,6}` plus `/proc/self/fd` for listening sockets the process owned (Linux-only) and, failing that, by scraping the URL a throwaway session posted — a session spent purely to learn a port. Now the server writes `<runtimeDir>/<projectKey>-<pid>.json` (`{pid, hostname, port, directory, worktree, startedAt}`; `$XDG_RUNTIME_DIR` preferred, `os.tmpdir()` fallback, `PTY_RUNTIME_DIR` overrides) on bind and removes it on dispose, and the panel reads records for its own project and confirms each with `/health`. Three properties are deliberate. **No lock:** Bun exposes no `flock` and Windows has none, so liveness is the health probe — the file is only a hint, which is why the panel never treats a record as authority. **Readers never delete:** PID liveness is namespace-sensitive (a container's pid is invisible from the host) and a partial read is indistinguishable from corruption, so a record can only be safely removed by its owner; writes are atomic (temp + rename) so a reader never sees a half-written record. **Project key, then a scrape tie-break:** records are matched by canonicalised (`realpath`) `directory` — the precise key, so two instances of one worktree are not ambiguous — with `worktree` only a fallback; when several records still match, the caller's own opencode server is the only thing that can say which is theirs, so the instance-scoped `pty-show-server-url` scrape is kept for exactly that, and never runs on an unattended poll. The port's blocker to remember: on the V2 API `ctx.worktree` is a `WorktreeDomain` **object**, not a path — the project directory is `ctx.location.directory` — and feeding the object to `createHash` threw, taking server creation (and the sidebar's own bootstrap command) down with it.
