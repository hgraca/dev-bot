## Load a child project's active memory when a monorepo session starts work in it

A monorepo session auto-loads only its own `AGENTS.md` and `<devbot_dir>/memory/active/**/*.md`; a child's always-on context was reachable only through `search-memories --focus`, which is search rather than context. `devbot tool project-memory <path>` closes that gap: it resolves the owning project (same longest-prefix rule as `project-for-path`), prints `AGENTS.md` and/or `CLAUDE.md` when present, then `<devbot_dir>/memory/active/**/*.md` sorted by path relative to the project — each labelled, under a scope line — exits `3` for an unregistered path, and exits `0` with a "no active memory" notice when the project has none. The rule carried by `devbot.md`, `teamlead.md`, `gather-context` Step 0, `memory-management` and `docs/monorepo-sessions.md` is load once per project per session, before the first read or edit of that project's **own** files (resolution and config reads are exempt); the content governs only that project — never a sibling, never the monorepo's coordination work, never copied into another vault — and a child rule beats the monorepo's while acting inside the child. Subagents sent into the child run the tool themselves; a scout report does not stand in for the orchestrator loading it. Symlinked instruction and memory files are still read — a project may deliberately link shared module memory in, and its own harness follows the same symlink — and are labelled with their resolved target so the scope claim stays accurate; rejecting them would have hidden rules the child itself loads. Listing order is a post-collection sort on the relative path, because `os.walk` yields a directory's files before descending, so per-directory `sort()` is not path order. There is no hook, guard or session state: enforcement is the instruction plus the tool.
