## `datasources` sidecars are gated by demand, not only by module enablement

A sidecar was rendered from the **full** global catalogue and started **machine-wide** by `datasources/up.sh`, whatever any project opted into. The only gate was module enablement (ADR `20260914222815`), but `datasources` is ONE module covering many datasources: disabling it to shed an unused sidecar would also drop the toolbox engines a project does use. Measured on the maintainer's machine: `opensearch-prod` and `s3-prod` were resident at ~360 MiB idle while the toolbox gateway itself was not even running, because the only project that opts into them is `observability` and no sidecar was tied to whether that project was open.

The decision is **two gates over one rule**. `demand.py` answers "which sidecars does this set of opt-in lists want?" — `demanded_sidecars` for the wanted names, `filter_demanded_sidecars` to drop the rest from a catalogue. The **render gate (A)** is static: a sidecar is rendered into `storage/datasources/docker-compose.yml` only when an existing path in `.devbot.global.jsonc::projects`, or the project being rendered, opts into it. The **run gate (B)** is live: a sidecar runs only while a live session's project wants it. The session registry now records the project each session serves (`_devbot_session_register` writes it, `_devbot_live_session_projects` reads it), and the running set is reconciled to that demand at boot (`up.sh`) and at session exit (`reconcile.sh`, run by the session registry through the generic module runner, inside its lock, with `_DEVBOT_REGISTRY_LOCK_HELD` so a module never re-locks the directory).

The render gate is deliberately **session-independent**. `datasources/init.sh` allocates the sidecar ports — and therefore the manifest URLs — from the same filtered catalogue `render.sh` uses, and `init.sh` runs during reinit, BEFORE the session registers. A live-session-dependent render universe would let render and init disagree, drifting a manifest URL from the port its service actually binds. The accepted consequence: a project absent from the `projects` list is invisible to the render gate, so its sidecars are not rendered while another project renders.

The reconcile reads the running set from **docker** (`docker ps --filter name=dev-bot-datasources-`), not from the rendered compose: a leftover whose datasource is no longer rendered is no longer a compose service, and it must still be reclaimed. An unwanted sidecar is `docker stop`ped rather than removed — the container is disposable and its state is not on the container. The boot reconcile holds the registry lock across its snapshot and its stop, so a session exit's stop — which takes the same lock — cannot interleave with it. The **start** direction is not ordered: a boot that overlaps an exit can leave one container without a consumer until the next reconcile. That is an orphan, never an outage.

Three consequences follow. A sidecar now stops when its last consumer exits, so a `devbot up` in a project that wants nothing no longer resurrects another project's sidecar. Because a sidecar now starts and stops with sessions, a **shared `uv` cache** ships with this change (`UV_CACHE_DIR` at `storage/datasources/uv-cache`, mounted by `render_compose.py`): `opensearch-prod` was the only container in the toolkit that resolved its dependencies at startup (`uvx`), re-downloading 69 packages on every start. Finally, this supersedes the "module-level gate is the only gate" conclusion of ADR `20260914222815` **for sidecars**; the sidecar class itself (ADR `20260926120100`) is unchanged apart from being demand-gated.
