## Every shell channel is guarded and measured, and the bash-vs-PTY rule is one shared skill

PTY capability comes from the third-party `opencode-pty` plugin (pinned in `opencode.dist.jsonc`), not from a dev-bot tool or skill, and the bash-vs-PTY rule had been written inline into three agent files as three tailored variants. The rule is now a single context skill, `devbot:shell-strategy`, loaded at session start by every agent that can run a shell command — the nine whose frontmatter does not deny `bash`. The stance is unchanged: the bash tool for quick, deterministic commands, a PTY for commands that may outlive the bash timeout (test suites, builds, migrations), prompt for input, or need output watched while they run. The distinction is time, not command length. A cross-cutting test derives "shell-capable" from frontmatter, so an agent added later cannot silently miss the rule, and it fails if the PTY detail is copied back into an agent file.

Guards were bash-only, which would have made "use the PTY" a way to delete the `rm -rf`/`sudo`/force-push net. Inspecting the compiled opencode binary settled the mechanism: every tool built from the agent's registry — plugin tools included — is wrapped so `execute()` first fires `trigger("tool.execute.before", {tool, sessionID, callID}, {args})`, so PTY calls do reach the hook; but the adapter read a single `command` field, while `pty_spawn` splits the executable from its argument array. `commandString()` now normalises each channel into the string the rules engine already consumes — bash → `command`, `pty_spawn` → `command` + `args`, `pty_write` → `data` (the interactive channel is a shell channel) — and the manifest matcher lists `bash`, `shell`, `pty_spawn`, `pty_write`. Coverage is strongest on `pty_spawn`, where the whole invocation arrives as one string. `pty_write` is explicitly best-effort: the hook sees the raw input before the plugin parses escape sequences and extracts command lines, so a command split across two writes, or one relying on a literal `\n`, is not segmented the way the rules engine anchors. It catches a plainly typed dangerous command; it is not a guarantee against a determined evasion.

Stats had the same blind spot: argument aggregation was gated on a literal `('bash','skill','grep','glob')` list and the renderer kept its own hardcoded tool list, so adding a tool to one place silently hid it. `_ARG_TOOLS` is now the single source for the SQL gate and the aggregation, `pty_spawn` is folded in through the same `program subcommand` normalisation as bash, and the renderer renders whatever the adapter supplies.

`permission.bash: deny` blocks only the bash tool, so `architect`, `critic`, and `po` each kept a full shell through `pty_spawn`. opencode-pty does gate its own tools: `permissions.js` calls `checkCommandPermission`, which reads the **global** `permission.bash` from `client.config.get()` and applies the structured patterns to the command and its args, treating `ask` as deny because the plugin cannot prompt. It reads only that global block — never the per-agent permission — so an agent-level `bash: deny` is invisible to it. A per-agent rule is still the right lever, for a different reason: opencode filters the tool registry with `disabled(Object.keys(tools), merge(agent.permission, permission))`, so a rule with `action: deny` removes the tool from the agent entirely. All five PTY tools are denied on those three agents (the deprecated `tools: {…: false}` map would have worked too).

Two PTY hazards are recorded in the skill rather than left to be rediscovered. `tool.execute.after` early-returns unless the tool is `bash`/`shell`, so a `git commit` run in a PTY skips the `command.after` hooks — the post-commit memory capture and the graph reindex — hence: commit through bash. And `shell.env` injects `DEV_BOT_SESSION_ID` into the bash tool only, so a PTY session does not inherit it. Known gap, since removed: guard rules carried an optional `agent` field, but `OPENCODE_AGENT` was set nowhere (claudecode hardcoded `""`), so a scoped rule could never match. The field, the `--agent` flag, and both harness's plumbing are gone; a config still carrying the stale key keeps working, with the rule now applying to every caller — fail-closed, it blocks more, never less.
