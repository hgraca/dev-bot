# A syntactic classifier cannot prove a semantic refactor rule — gate on the compiler

The `promote-readonly` op decides "assigned only in the constructor" from a syntactic classifier over `findReferencesAsNodes()` plus an assignment-operator check. It is wrong in ways no amount of classifier tightening fixes: a write through element access (`this["x"] = 1`) or `delete this.x` is not even in the reference set; a `static` field written from the *instance* constructor looks like a legal constructor write that `readonly` forbids; and `Object.assign(this, …)` / `Reflect.set` / `defineProperty` leave no trace at all — the first two fail to compile, the last is silent. The fix that generalises is a **diagnostics gate**: collect `project.getPreEmitDiagnostics()` into a key set (file + line + code — line rather than offset, since the edit shifts columns) *before* mutating in memory, mutate, re-collect, and refuse the apply when the change introduces a new error. Refusing means `fail()` and never `project.save()`, so a one-shot driver writes nothing. Pair it with the cheap precise fixes (only assignment operators count as writes, so `this.x === 0` is a read; a class whose constructor assigns through `Object.assign`/`Reflect.set` is ineligible) so the gate rarely fires. The gate is all-or-nothing — one refusing property blocks its class's whole promotion — but it replaces "we hope the classifier is complete" with "the compiler agreed". The same reasoning applies to any op whose rule is semantic: `privatize-members` and the unused-removal ops all decide from a compiler-resolved reference set, and a reference the compiler cannot see is invisible to them.
