# Audit 61/62 fix session: byte-idempotency capture, codebase-memory UI, stale list tests

Audits 61 (opencode) and 62 (claudecode) both came back PASS with zero FAILs — only NOTEs. This records what was fixed and the non-obvious mechanisms, so future audits re-verify instead of re-flagging.

## Byte-idempotency evidence is now captured, not just printed

The audit mandate forbids running `devbot reinit`, so §1 byte-idempotency was always NOT-RUN — the launcher's double-reinit probe printed `BYTE-IDEMPOTENCY-PASS/FAIL` to stdout only, and nothing survived for the session. Now `test-reinit.sh` (run in the disposable container BEFORE the harness starts) calls `byte_idempotency_report` (`tests/test-project/test-lib.sh`): it SHA-256s each generated file after reinit #1 vs #2, writes the per-file byte values + verdict to `.agents/logs/byte-idempotency.log`, and returns 0/1. At harness start `_devbot_rotate_session_logs` moves it into `.agents/logs/rotated/`; `audit.md` §1 reads either path and reports PASS/FAIL citing the hashes, falling back to static guards + NOT-RUN only when absent. Key detail: rotation only happens when `start.sh` runs, so the opencode headless path (`opencode run --command`, no `start.sh`) leaves the live file in place — hence the audit checks BOTH paths. Unit test: `bin/tests/byte_idempotency_report_tests.bats`. Commits `e48a18c5`, `784016f6`.

## codebase-memory graph UI fixed port → launch with --ui=false

`codebase-memory-mcp` serves an optional HTTP graph UI on a fixed loopback port (config `ui_port` = 9749). dev-bot launches one stdio server per project, so the second instance cannot bind and `cbm-daemon.log` fills with `ui.unavailable port=9749 reason=in_use` plus an unbounded 30 s `ui.retry_scheduled` loop (MCP tools themselves are unaffected). Fix: `src/agentic/codebase-memory/mcp.json` launches `codebase-memory-mcp --ui=false`. Caveats: the flag persists account-wide, and `--help` claims `ui_enabled default=false` while the effective value can be `true` — verify with `codebase-memory-mcp config get ui_enabled`. Commit `b9660b9d`.

## `devbot list` tests hardcoded the qmd engine

`bin/tests/commands_tests.bats` asserted `| qmd` in `list mcps` and `list tools`. But the shipped default is `memory_search_provider=mdctx`, and qmd/mdctx are mutually exclusive (`_devbot_get_disabled_modules` appends the non-selected engine to the disabled set). `list mcps` filters module definitions by that set → only `mdctx` shows; `list tools` reads the physical `.agents/tools/` farm, which has no qmd tool while qmd is disabled (and mdctx ships no tool at all). Fix: pin `DEVBOT_MEMORY_SEARCH_PROVIDER=mdctx` in the mcps test and assert `| mdctx` + `refute | qmd`; assert the always-wired `| search-memories` in the tools test. General rule: tests that name a memory/codebase engine must pin its provider via the env override (`DEVBOT_MEMORY_SEARCH_PROVIDER`), never hardcode a default that can flip. Commit `c522fa35`.

## False positives worth not re-chasing

- Audit-61 N1 (`.devbot.project.sha` "tracked but not ignored"): false — git also honours `.git/info/exclude`, which lists it; `git ls-files`/`git status` show it untracked and clean. Check `git check-ignore`/`ls-files`, not just `.gitignore`.
- Audit-61/62 `private_dir_group_writable_ancestor mode=0775`: already fixed in `tests/test-project/Dockerfile` (`chmod g-w /home/ubuntu/.cache`, audit-60 NOTE-2); the audits ran an image built before that.
- graphify 0.8.35-vs-0.9.58 skill mismatch: the stale copy is user-global `~/.claude/skills/graphify`; the report's suggested fix (`graphify install --platform claude`) would recreate the unnamespaced skill `graphify/init.sh` deliberately deletes. Needs a maintainer call, not an auto-fix.

Note: on this machine `.git/info/exclude` contains `storage/global-memories/**`, which shadows NEW files in the shipped global store (the existing 613 files are tracked, but a new one needs `git add -f`). That is why the reusable codebase-memory UI lesson lives here instead of `global/mcp/`.
