## redis_exporter in cluster mode: `--is-cluster` does not fan out, and ElastiCache denies `CONFIG`

Three facts that decide a Redis monitoring design, each verified against the exporter README and a live cluster. **(1) `--is-cluster` does not make `/metrics` report every node.** It only enables the discovery endpoint; per-node metrics require the Prometheus http-sd pattern — scrape `GET /discover-cluster-nodes`, then scrape each returned node through `metrics_path: /scrape` with relabels mapping `__address__` → `__param_target`, `__param_target` → `instance`, and `__address__` → the exporter service. With a static scrape you see only the single node in `--redis.addr`, so a cluster looks healthy while its other shards are invisible. The OTel prometheus receiver supports this because it accepts the full Prometheus `scrape_config` including service discovery. Note `--is-cluster` failing this way is silent: the endpoint 404s and no metrics arrive. **(2) `instance_role` is `master` / `slave`**, not `replica` — so a filter selecting the primary must be written `instance_role="master"`, and aggregating a metric across nodes without that filter double-counts: replicas report the same counters, so a summed `used_memory` divided by a single node's `maxmemory` reads roughly 3× on a 1-shard/3-node cluster. Per-node panels are fine; only ratios that aggregate need the filter. **(3) AWS ElastiCache denies `CONFIG` and `DEBUG`** (but permits `INFO`, `CLUSTER INFO/NODES/SLOTS`), so every config-derived metric is empty — pin `--config-command="-"` to skip it deliberately rather than erroring, and prefer INFO-derived metrics, e.g. `redis_memory_max_bytes` (from INFO `maxmemory`) instead of `redis_config_maxmemory`. ElastiCache also returns **IPs** in `CLUSTER NODES` whereas a self-hosted cluster often announces a hostname, which makes the ElastiCache scrape DNS-independent and the hostname-based one dependent on cluster DNS.
