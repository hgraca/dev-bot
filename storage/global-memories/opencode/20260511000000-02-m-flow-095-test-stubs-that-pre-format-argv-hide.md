Cycle A of the init-create-codebase-report story. The architect's plan (§1.4 Decision 1, Step 1 line 178) mandated `"${_explore_prompt}"` quoted as a single argv to `opencode run`. The developer's Round 1 implementation wrote `${_explore_prompt}` unquoted at `bin/init.sh:316`. Tests passed (16/16) because the stub recorded argv via `printf ' %q' "${_a}"` which loop-formatted each token onto one log line — making 13 word-split tokens indistinguishable from 1 quoted token in the assertion (`grep -F 'Use the create-codebase-report skill ...'` matched either way). The defect was caught only at human-reviewer R1 by reading the production source line. Round 2 fix: quote the variable AND change the stub to `printf '%s\n' "$@"` with `argv-begin`/`argv-end` delimiters so each token is one log line — the multi-word prompt then asserts as a single literal line (true regression protection).
When a test stub formats subprocess argv for logging, the formatter shape determines whether word-splitting bugs are visible. Token-per-line formatters (`printf '%s\n' "$@"`) make argv-count assertions possible and surface word-splitting; token-per-space formatters (`printf ' %q' "${_a}"` in a loop, or naive `"$*"`) collapse the difference between "1 quoted arg" and "N split args" into the same string. Diagnostic when designing a stub: can a `grep -c argv-token-count` or a single literal-string match distinguish quoted-as-one from unquoted-as-many? If not, the stub is hiding the shape of the bug it should catch. The test-shape-dictates-prod anti-pattern (M-FLOW-093 parent) has a sibling here: test-stub-shape hides prod defect.
