## opencode-pty binds a random port and publishes it only by posting a chat message

`opencode-pty` is the only window onto PTY sessions, and it starts its HTTP server as a side effect of one of two slash commands: `pty-show-server-url` (which **starts the server and posts the URL as a chat message** — visible clutter on every opencode start) and `pty-open-background-spy` (which starts it and opens a browser instead). The port is `Bun.serve({ port: 0 })` — random, and published nowhere else (no kv, no file, no env). Do **not** scrape the message as the primary strategy; read the OS instead. The plugin runs in the same process as the server, so its own listening sockets are enumerable: collect socket inodes from `readlink /proc/self/fd/*` (`socket:[N]`), match them against `0A` (LISTEN) rows in `/proc/self/net/tcp6` + `/proc/self/net/tcp`, and identify the server by probing each candidate's `/health` for `{"status":"healthy", "sessions":{…}}` — a loopback port may belong to something else entirely (CUPS answers on `[::1]:631`). Honour `PTY_WEB_HOSTNAME` when set, since that is what the server binds. Off Linux there is no `/proc`, so the fallback is to run the message-posting command inside a **throwaway session** (create → command → scrape that private session → delete it): the server is plugin-level and survives the session's deletion, and the user's transcript stays clean. API shapes: `GET /api/sessions` (array; items carry `id,title,command,args,workdir,status,pid,lineCount,exitCode,notifyOnExit,timedOut,createdAt` — **no owning opencode session id**, so the list cannot be scoped per session), `GET /api/sessions/:id/buffer/plain` → JSON `{plain, byteLength}` with CRLF content (not a raw body), `…/buffer/raw`, `POST …/input`, `POST /api/sessions` `{command,args?,description?,workdir?}`, `DELETE /api/sessions/:id`. `status` is not just running/exited — it also reports `killing` and `killed`, which carry no exit code.
