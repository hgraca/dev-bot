The `remember-session` plugin injects a synthetic user message (`CAPTURE_PROMPT_TEXT`) on `session.idle` to trigger memory capture. Original prompt said "do not report results to the user" but never said what to do _after_ capture. Result: the agent treated the capture as the entire new task and halted, even when it had been mid-workflow (e.g. between iterations of `implement-story`, awaiting subagent return). Symptom looked like a stall but was a missing directive. Fix: every plugin-injected prompt that interrupts ongoing work must carry both halves — what to do _and_ what to do after. For remember-session this meant (a) expanding `CAPTURE_PROMPT_TEXT` in `src/plugins/remember-session.js` to instruct silent resumption of the next pending step, or silent stop if nothing is pending; and (b) adding a matching step 7 ("Resume after automated capture") to `src/skills/memory/remember-session/SKILL.md` so the rule survives whether the agent reads the prompt or the skill in isolation. Two-surface fix is deliberate: synthetic-prompt agents may load the skill and forget the prompt, or follow the prompt and skim the skill — both surfaces must agree. The rule is gated on the `[DevBot]` prefix so manual "wrap up" still produces a report and stops normally. See [[ADRs]] M-ARCH-034 (no shared module between plugins — duplication is acceptable here) and `tests/plugins/remember-session.test.ts` (only asserts `[DevBot]` substring, so multi-line prompt expansions are safe).

The `remember-session` plugin fires on `session.idle` by injecting a synthetic user message (`CAPTURE_PROMPT_TEXT`) telling the agent to load `remember_session` and run it silently. Symptom: agent ran the capture, then HALTED — even when it was mid-workflow (e.g. between iterations of `implement-story`, awaiting subagent return). Root cause: the agent treats an injected user message as the entire new task scope. After fulfilling the capture instruction, it has no directive telling it what to do next, so it stops as if the user's request is complete. The skill's instructions alone are not enough; the synthetic prompt itself must carry the resume directive, because the prompt is what scopes the agent's "current task." Fix (commit `fbe229d`): two-surface change — (1) expand `CAPTURE_PROMPT_TEXT` to multi-line: load skill, run silently, AND "if work was in progress before this prompt arrived, silently resume the next step; otherwise stop with no output"; (2) add step 7 to `src/skills/memory/remember-session/SKILL.md` formalizing the resume-vs-stop rule, keyed off the `[DevBot]` prefix so manual "wrap up" still produces its report. Both surfaces needed because either may be read in isolation. Generalises to any plugin that injects synthetic user prompts: the prompt must explicitly instruct continuation behavior, not rely on the agent inferring it from prior conversation state.
