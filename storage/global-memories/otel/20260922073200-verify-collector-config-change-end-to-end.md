## Verifying an OTel collector config change: render, validate, simulate with a control, then prove the live path

A collector config change can be verified far beyond inspection before it ever ships, in four steps that each catch a different class of failure. **(1) Render what actually deploys** — `helm template <release> <chart> --version <v> -f <values>` and confirm the new statement reaches the rendered config by grepping a non-wrappable marker; a change to inline Helm values can silently drop if it lands outside the chart's expected key path. **(2) Validate with the exact image the chart deploys** (`docker run --rm -v cfg:/cfg.yaml:ro <collector-image> validate --config=/cfg.yaml`) — parseable environment-dependent errors (missing `/hostfs`, empty OTLP endpoint, unset `K8S_NODE_NAME`) are expected outside a cluster and do **not** mask processor errors, so the signal is the absence of OTTL/component errors. **(3) Simulate behaviour**, not just validity: a minimal `filelog → transform → debug` config fed the real log line **plus a negative control line**, asserting the expected severity and an intact body — this is what proves an override is narrow rather than blunt, and it catches wrong-field/never-fires conditions that validation cannot. **(4) Prove the live path after deploy**: confirm the pods actually rolled (Helm's `checksum/config` annotation on the pod template is what forces it — without it a ConfigMap change never reaches the running pods), then generate one matching record deliberately (a single request mimicking the traffic) instead of waiting for organic traffic, and compare against a pre-deploy row of the same shape for a clean before/after. Organic traffic is a poor verification oracle: bursty sources can leave you with zero observations for tens of minutes right after a rollout.
