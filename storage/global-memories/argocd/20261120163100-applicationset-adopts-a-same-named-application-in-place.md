## An ApplicationSet adopts a same-named Application in place — no orphan-delete dance needed

When migrating a hand-made Argo CD `Application` into a directory generated by an `ApplicationSet`, the usual worry is that the controller cannot create its Application because one already exists, and that the obvious fix — delete the old one — cascades to the workloads.

Neither is needed **as long as the generated name matches**. The ApplicationSet controller takes over an existing Application of the same name: it sets its owner reference and rewrites the spec (path, destination, and its own `syncPolicy`). The workloads are never touched, so there is no delete, no `--cascade=orphan`, and no gap.

What actually breaks is a **name change**. An Application name that no longer matches any generated one is left behind — still pointing at its old path, now missing — and it is never cleaned up automatically. So before moving anything, make the directory basename equal the existing Application name; rename the directory only when you intend the rename, and delete the stale Application with `kubectl delete application <name> -n argocd --cascade=orphan` if you want its resources kept.

A generated Application containing an Application of the same name cannot work at all: an app-of-apps whose directory is named after one of the Applications it defines collides with itself, so name that directory differently (e.g. `agent-gateway` for a directory holding `agentgateway`).
