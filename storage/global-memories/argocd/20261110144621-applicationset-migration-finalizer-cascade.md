## Changing an ApplicationSet's directory layout deletes its Applications — orphan the old set first

Every Application generated by an ApplicationSet carries `resources-finalizer.argocd.argoproj.io`, so deleting the Application object deletes the workloads it manages. The generator's glob decides which directories are desired: the moment a commit moves `src/<ns>/<app>` to `src/manifests/<ns>/<app>`, the old set's `src/*/*` no longer matches the old paths, and its very next reconcile treats those Applications as extraneous and deletes them — cascading into the running services. The safe order is: `kubectl delete applicationset <old> --cascade=orphan` **before** merging the layout change (the Applications survive, orphaned, and keep syncing), then merge, then apply the new set(s), which adopt the still-existing Applications by name. Two related facts make this work: the Application name is the directory basename, so keeping the basename keeps the same Application object and turns a move into an in-place spec update; and child Applications that were created by a *hand-made* App (no finalizer) can be pruned and recreated harmlessly — only the Application objects go, the pods survive and are adopted back. Never rename the Application or the ApplicationSet as part of a layout change: a rename is a delete plus a create, and only the orphan step prevents the cascade.
