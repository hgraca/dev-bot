## An ArgoCD sync blocked on a workload's health gate wedges every later revision — and cannot be cleared by patching `status`

An `automated` ArgoCD app syncs one revision at a time: if the running operation is stuck waiting for a resource to become healthy (`waiting for healthy state of apps/StatefulSet/<name>`), the controller **resumes that same operation** instead of starting a new one, so every later commit to the app's path is queued behind it indefinitely — the logs show a hot loop of `Resuming in-progress operation` → `Syncing` → `sync/terminate complete` roughly once a second, and the fix never applies. The operation is pinned to the revision it started on (`status.operationState.operation.sync.revision`), so if **that** revision's manifest is what blocks the health gate, the app deadlocks: it is waiting on the very problem the newer commit fixes, and `status.sync.revision` will already show the newer commit while nothing is applied. Two things make the obvious remedies fail. First, patching `status.operationState.phase` to a terminal value does **not** clear it — the controller overwrites the patch on its next reconcile because it still holds the operation in progress; the supported lever is `argocd app terminate-op` (CLI/UI). Second, the ArgoCD `Application` CRD commonly declares **no `status` subresource** (`spec.versions[*].subresources` is `{}`), so `kubectl patch application <name> --subresource=status` fails with `NotFound: applications.argoproj.io "<name>" not found` despite the object existing — a plain merge patch with no `--subresource` flag is what actually writes status. The fastest practical unblock is to make the blocked resource healthy (e.g. patch the live workload so its pod can schedule): the resumed operation then completes, records its revision in history, and ArgoCD syncs the pending HEAD on the next reconcile.
