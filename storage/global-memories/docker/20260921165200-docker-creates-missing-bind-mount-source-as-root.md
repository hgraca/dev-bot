## Docker creates a missing bind-mount SOURCE on the host as root:root

Mount a host path that does not exist and the daemon creates it owned by `root:root`, even when the invoking user is uid 1000 or 501 (`docker run --rm -v /tmp/x/missing:/data node:22-slim ls -ld /data` → `drwxr-xr-x 2 root root`). That stays invisible until a service runs as the HOST uid (`user: "${DEV_UID}:${DEV_GID}"`) and validates ownership of its own state dir: `codebase-memory-mcp` refused to start on a fresh macOS install with `exact executable identity could not be verified (cache-private) - /Users/<user>/.cache/codebase-memory-mcp: owner uid 0, expected euid 501`, so the MCP gateway never answered and the module's `up.sh` timed out after 30 s with only "gateway not reachable". The trap is fresh-machine-only — where the dir already exists the daemon never creates it, so nothing looks wrong on a warm machine, and an existing image/dir means nobody re-examines it. Fix by creating every WRITABLE bind source yourself, as the host user, immediately before compose runs (`mkdir -p -m 700 <source>`, then `docker compose up`); doing it in a module `up.sh` is too late, because the containers — and the daemon-created dir — already exist by then, so it must run before the compose invocation. For READ-ONLY mounts do the opposite: long syntax `type: bind` + `read_only: true` + `bind: {create_host_path: false}` (only under `bind:` — at the volume level compose rejects it with `additional properties 'create_host_path' not allowed`) so a genuinely missing input fails loudly instead of being mounted as an empty root-owned directory. Diagnose a suspect mount with `ls -ldn <host-path>` and `docker inspect --format '{{json .Mounts}}' <container>`; if the host side is user-owned but the container reports uid 0, the cause is the file-sharing layer (Docker Desktop/virtiofs) rather than the daemon — a different problem the pre-create does not address.
