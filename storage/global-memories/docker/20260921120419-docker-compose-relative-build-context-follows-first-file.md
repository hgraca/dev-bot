## A relative `build.context` (and a relative `include:`) resolves against the FIRST `-f` file's directory, not the file's own

With `docker compose -f a/docker-compose.yml -f b/docker-compose.yml up`, a **relative** path inside `b` — `build.context: .` and a relative `include:` alike — resolves against **`a`'s** directory. So a per-module compose that keeps its `Dockerfile` beside it and declares `build: { context: . }` silently builds from whichever file happened to be listed first, and the build dies with `failed to solve: failed to read dockerfile: open Dockerfile: no such file or directory`; BuildKit's progress line for it reads `transferring dockerfile: 2B` — 2 bytes is the failure signature, not a truncated or corrupt Dockerfile, so do not go hunting for one. Verified on Compose v2+: `docker compose … config --format json` prints the resolved `build.context`, which is the cheap way to see it without building. The trap is latent, which is what makes it expensive — `up -d --no-recreate` only builds a service whose image is **missing**, so any machine that already has the image never builds and never fails: it surfaces on the first run after a fresh clone or `docker rmi`, i.e. on a new machine, never the author's, and a single-file invocation (`docker compose -f b/docker-compose.yml build`) hides it too because then the project directory really is `b`'s. Fix it by anchoring the path absolutely — `build: { context: ${DEV_BOT_ROOT}/src/agentic/<module> }`, or whatever variable the calling script exports, set in the environment that runs compose — or by using `include:` instead of stacking `-f` files, since an included file *is* given its own path base (verified). Never leave `context: .` in a compose that gets merged with others, and confirm the fix with `docker compose -f <other> -f <yours> config --format json`.
