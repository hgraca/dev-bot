Third blob-corruption recovery technique, complementing L1027 (`hash-object -w` when working-tree SHA matches) and L1050 (cherry-pick from dangling commits). Symptom variant: `git commit` fails with `error: invalid object 100644 <sha> for '<path>'` AND `git fsck --no-dangling` reports `missing blob <sha>` AND `git ls-files --stage <path>` shows the missing SHA — but the working-tree file is intact and unmodified. The corruption lives in the INDEX only; HEAD's tree is fine. Root cause this session: PhpStorm rebase wrote new blob SHAs into the index without flushing the corresponding objects to `.git/objects/`. Recovery without losing working-tree content: (1) `git rm --cached <files>` to drop the corrupted index entries (working-tree files preserved as untracked); (2) `git reset HEAD <files>` to restore the index entries from HEAD; (3) `git status` should now show the files as `M` (modified) again with the working-tree changes intact; (4) `git fsck --no-dangling` returns clean; (5) `git add` + `git commit` works normally. Validated this session on `src/agents/reviewer.md` and `src/agents/tester.md` after commit `46468c0` first attempt failed with `invalid object 24f20a0bdec...`. Why this technique exists: when corruption is index-only, neither L1027 (working-tree SHA differs from index SHA, so `hash-object -w` writes a different blob than what the index demands) nor L1050 (no dangling commits to cherry-pick from) help. Cross-ref L1027, L1042, L1050, L1053. See [[memories]].

Fourth blob-corruption variant in this repo (cf. L1027, L1050, L1072, L1077). Symptom: `git status` runs fine and shows staged + modified files, but every command that walks the index — `git diff --cached`, `git diff --staged`, AND CRUCIALLY `git reset` itself — fails with `fatal: unable to read <sha>`. `git fsck --no-dangling` reports `missing blob <sha>` for several blobs. Recovery techniques L1072 path A/B and L1077 do NOT apply: they all require `git rm --cached` or `git reset HEAD <path>` to succeed, and those commands also walk the index and fail with the same error. The only recovery: (1) `rm .git/index` directly — this deletes the staging area only, working-tree files are untouched; (2) `git reset` rebuilds the index from HEAD's tree; (3) `git status` now shows working-tree files as Modified (any prior staging is lost — anything pre-staged before the corruption must be re-staged); (4) re-stage the intended files with `git add <files>` and commit. Validated this session: index referenced 3 missing blobs (`dfd6edb4...`, `2fafdff0...`, `d4396113...`), every git command except `status` and `fsck` failed, `rm .git/index && git reset` recovered cleanly, all working-tree edits preserved. Likely root cause this case: a prior `setup-iteration.sh` SIGKILL (see existing gotcha for that script) may have interrupted git mid-write while staging snapshot files. **Decision tree for future blob corruption**: (a) if `git reset` works → use L1072 path A/B; (b) if commit fails but `git rm --cached` works → use L1077; (c) if even `git reset` fails → use this technique (rm .git/index). Cross-ref L1027, L1050, L1072, L1077. See [[memories]].
