## A fixup far from its target cannot be folded — diagnose it, then reword it instead

`git rebase -i --autosquash` folds a `fixup!` by cherry-picking it onto its target, and a cherry-pick's three-way merge base is the fixup's *parent*. When the fixup sits far from its target — commits in between having touched the same files — the merge base is the near-tip content while "ours" is the target-era content, so the entire backward delta surfaces as conflict hunks: one such fold produced ten structural hunks spanning two divergent lineages instead of one small conflict. Two cheap diagnostics decide whether a fold is possible at all, and should be run *before* attempting it. First, `git cat-file -e <target>:<path>` for every file the fixup edits — for four of five fixups the file did not exist at the target, because the marker's subject matched a commit that predates the code the payload corrects (a shared subject, or a fixup authored against a much later tree). Second, `git log -S '<line the fixup removes>'` to find which commit introduced it — when the payload spans several commits there is no single true target, so retargeting is not an option either. When folding is impossible, **reword rather than resolve**: a reword-only rebase (`GIT_SEQUENCE_EDITOR` writing `reword` for the chosen commits, `GIT_EDITOR` pointing at a script that swaps each message) reorders nothing, so every commit is replayed onto its own parent's tree and cannot conflict — which turns misleading `fixup!` titles into honest Conventional Commits with a byte-identical tree, and leaves the branch pushable as a fast-forward. Companion trap: on a delete/modify (`DU`) conflict, `git add <file>` stages the *worktree* file, which during a fold is the fixup's near-tip content — silently pulling a later state into an early commit (and it was that mistake, not the merge, that produced the ten hunks). For a fold the right side is the accumulator plus the fixup's own hunk, never the worktree wholesale. Verify every rewrite with a hash that must not change: `git rev-parse HEAD^{tree}`, or `git diff <base>..HEAD | git hash-object --stdin` when a rebase may have touched the base's descendants.
