## SigNoz log pipelines cap at six severity levels — NOTICE/11 is unreachable

A SigNoz log pipeline's `severity_parser` mapping key must be one of `trace`, `debug`, `info`, `warn`, `error`, `fatal`. The **create** route (`POST /api/v1/logs/pipelines`) validates this against `validMappingLevels` in `pkg/types/pipelinetypes/pipeline.go` and rejects anything else with `400 <key> is not a valid severity`; upstream `main` ships the same six, so no upgrade widens it. That makes the ceiling `warn`/13 or `info`/9 — OTel's `NOTICE` label cannot be produced by a pipeline at all, because the collector-side stanza severity enum (`pkg/stanza/entry/severity.go`) hardcodes severity 11 as `INFO3` and has no NOTICE entry (OTel has no NOTICE level; it is a syslog name in the INFO band). Even bypassing validation, `{"notice": [...]}` yields text `notice` with `severity_number: 0`, and `{"info3": [...]}` yields text `INFO3` with number `11` — the number without the label. `severity_parser` is also the only operator that writes severity: `add` cannot target `severity_text`, since its `field` must be prefixed `body`/`attributes`/`resource`. Two asymmetric-tooling traps amplify this: **`/preview` skips the create-time validation**, so `info3` previews as `severity_number: 11` but is rejected by create — preview validates operator *behaviour*, never operator *legality*; and **`/preview` silently skips pipelines with `enabled: false`**, so to validate a disabled pipeline set `enabled: true` in the preview payload only. Multi-operator pipelines must also set `output` to the next operator's `id` on every non-final operator (`400 output of operator <id> cannot be nil`), and an empty `"id": ""` in a preview payload fails UUID decoding with `failed to decode request body` (omit `id` entirely for a new pipeline). Auth on these routes is a service-account key in the `SIGNOZ-API-KEY` header — session JWTs (`Authorization: Bearer`) return 401 here.
