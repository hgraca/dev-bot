## SigNoz's Database Calls pane needs the legacy `db.system`, while modern PHP OTel emits only `db.system.name`

The service page's **Database Calls** pane (`Services → <service> → DB Call Metrics`) populates *only* from spans that carry the **legacy** span attribute `db.system` and are not `span.kind = 2` (SERVER) — there is no client-side DB metric behind it, so an empty pane always means a missing attribute, never dropped data. The PHP auto-instrumentation has moved to the newer database conventions: `opentelemetry-auto-pdo` 0.4.0 and `opentelemetry-auto-laravel` 1.7.0 write **only** `db.system.name` (sem-conv 1.38 marks `db.system` deprecated), so every PHP service shows an empty pane while its DB spans flow normally — one production service carried ~3M spans per 30m with `db.system.name` and **zero** with `db.system`. Non-PHP instrumentations (redis, mongodb) still set the old key and keep populating, which makes the gap look service-specific when it is not. Bridge it collector-side with an OTTL `transform` processor on the agent's traces pipeline that sets `db.system` from `db.system.name`, guarded on `db.system == nil` (never clobber a client-set value) and on `db.system.name != nil` (a non-DB span must never grow a DB system). Three traps: SigNoz cannot backfill an attribute onto already-stored spans, so history stays empty and the pane fills only from the rollout forward; naming a `traces` pipeline in the SigNoz `k8s-infra` chart **replaces** the chart's default processor list rather than extending it, so `batch` must be repeated or batching is silently dropped; and an instrumentation may write a non-standard value into the new key (see the Laravel QueryWatcher connector-alias entry), so an allow-list or an explicit mapping is safer than a blind copy. Verify coverage with `db.system.name EXISTS AND db.system NOT EXISTS` → 0.
