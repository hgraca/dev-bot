## Two k3d clusters exhaust Linux default `fs.inotify.max_user_instances=128`

Linux default `fs.inotify.max_user_instances=128` is exhausted by a single k3d cluster (server + agents each consume tens of inotify instances via k3s controllers, kubelet, containerd, CoreDNS, traefik, etc.). When a second k3d cluster starts, its containerd fails to initialise — symptom in container logs: repeated `Waiting for containerd startup: rpc error: code = Unimplemented desc = unknown service runtime.v1.RuntimeService` paired with `error creating fsnotify watcher: too many open files`. Downstream effect: kubelet never registers the node (`Error from server (NotFound): nodes "k3d-…-server-0" not found` in server logs), no nodes appear in `kubectl get nodes`, all system pods (CoreDNS, traefik, local-path-provisioner, metrics-server) stay `Pending` forever, and `make up-producer` fails at `kubectl rollout status deployment coredns --timeout=120s`. The second cluster's k3d container shows `1/1` in `k3d cluster list` (server container is up) but the cluster is functionally dead. Trap: increasing `max_user_watches` (already at 524288 by default on most distros) does NOT help — the limit hit is the lower `max_user_instances`. Discovery method: `find /proc/*/fd -lname 'anon_inode:inotify' | wc -l` shows usage; `cat /proc/sys/fs/inotify/max_user_instances` shows the cap.
Fix: `_ensure-inotify` Makefile target persists `fs.inotify.max_user_instances = 512` to `/etc/sysctl.d/99-k3d-inotify.conf` on first invocation per machine (one-time sudo prompt) and silently no-ops on every subsequent call, including across reboots — agents can run `make up` non-interactively after the first operator-driven invocation. Wired as prereq of `_up-signoz-fresh` and `_up-producer-fresh`. The persist file's content cites this project so its origin is discoverable. Earlier policy was runtime-only/non-persisted (commit `24834f4`); reversed at user request because the runtime-only approach blocked agent-driven test cycles (sudo cannot prompt from the opencode sandbox). See `latent/PDRs.md` "Inotify limit policy: persisted to /etc/sysctl.d/, not runtime-only" and [[ADRs]].
