## A successful SigNoz `PUT` answers `204 No Content`, not `200`

Success checks that accept only `200` and `201` abort mid-apply against SigNoz. Creating returns `200`/`201`, but **updating an existing rule answers `204 No Content`** — so an upsert loop that applies many rules fails on the *first already-existing one*, and because it typically runs after the notification-channel step, it leaves the apply **half-done**: channels created, rules untouched. Observed as `ERROR: … — HTTP 204:` with an empty body, on `PUT /api/v2/rules/{id}`. Match the whole 2xx class (`[[ "$code" != 2* ]]` in bash) for create, update and disable paths alike. The reason this hides so long is that a `--dry-run` skips the requests entirely, so it previews clean forever and only ever fails during a real apply — which also means the only reliable test of an apply script is running it for real. The same pattern bit dashboard deletion later in the same session (`DELETE` → `204`).
