To find N+1 problems: first call `signoz_signoz_aggregate_traces` grouped by `name` to rank span names by count — the top names with disproportionately high counts (e.g., `PDO::prepare` 1M vs requests 700k) signal repeated queries. Then call `signoz_search_traces` with `minDuration` to find the slowest traces from the affected service. Finally call `signoz_signoz_get_trace_details` on those trace IDs and grep `"name":"` to count repeated span names within a single trace — identical model `::get` or `::find` calls appearing 3+ times confirm N+1 at the row level. Focus on the highest-count trace first; the 1.5MB+ trace files are the worst offenders.

To find N+1 queries using SigNoz: (1) Use trace aggregation `count() groupBy trace_id orderBy count() desc` to find traces with abnormally high span counts — a 200K+ span trace for a normal transaction is a definitive N+1 signal. (2) Use `signoz_get_service_top_operations` to find repeated operation names — uniform counts across related operations (e.g. 8,900× for 8 different Contract* sub-model gets) indicate a loop loading sub-models one by one. (3) Use `signoz_aggregate_traces` with filters on specific operation names to count per-trace repetitions. The biggest gains come from fixing the highest-call-count operations first.
